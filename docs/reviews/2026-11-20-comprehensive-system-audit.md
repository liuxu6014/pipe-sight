## 需要修复的问题

### 1. [P1] 后端镜像会包含本地环境文件和运行目录

- 位置：`deploy/docker/backend.pg.Dockerfile:9`；`backend/.dockerignore:1`。
- 原因：镜像执行 `COPY . .`，忽略列表没有排除 `.env*` 和 `.runtime/`。Git 的忽略规则不参与 Docker 构建。
- 触发：直接在当前实际运行目录构建后端镜像。只检查了文件是否存在及目录大小，未读取或输出真实密钥：该目录确有 `.env.dev` 和 `.runtime/`。
- 复现：复制当前 `.dockerignore` 到独立的合成构建上下文，放入虚构的 `.env.audit`、`.runtime/audit-backup.txt`，以 `FROM scratch; COPY . /context/` 构建并导出。结果两份合成文件均被复制。
- 影响：本地配置、可能包含敏感信息的运行产物会进入构建上下文和镜像层；镜像分发时可能泄露这些信息。
- 修复：采用明确的源码复制清单或完整排除环境文件、运行目录及备份；运行时注入配置。检查已有镜像是否已经分发，再决定是否需要重建及轮换受影响凭据。
- 验收：合成哨兵文件不能进入构建上下文/最终镜像，正常启动与 Worker 运行仍通过。不得为验证而用真实密钥构建测试镜像。

### 2. [P1] 自助修改密码可绕过旧密码校验

- 位置：`backend/src/app/system/schemas/user.py:183`；`backend/src/app/system/services/users.py:355`；入口 `backend/src/app/system/api/user_controller.py:393`。
- 原因：`ResetPasswordModel.old_password` 可空；个人改密接口直接把该值传给通用重置服务，服务仅在旧密码为真时执行校验。省略或传空字符串即跳过旧密码检查。
- 复现：使用实际请求 DTO 接受仅含 `newPassword` 的数据，按控制器相同方式构造 `ResetUserModel`，调用实际改密服务。DAO 与数据库均替换为内存对象，确认新密码哈希写入成功。
- 影响：持有已有登录会话的人可以在不知道旧密码的情况下修改该账号密码。这不是未登录访问漏洞，但扩大了会话泄露后的影响。
- 修复：自助改密请求必须在服务端要求非空旧密码及新密码；与管理员重置、找回密码场景分开处理，不能依赖前端必填规则。
- 验收：缺失、空白、错误旧密码均拒绝；正确旧密码才能修改；管理员重置与找回密码维持各自的权限/验证码校验。

### 3. [P1] 修改密码后已有会话仍能继续访问

- 位置：`backend/src/app/system/services/users.py:365`；`backend/src/app/system/services/authentication.py:180`、`:201`。
- 原因：改密只更新数据库；令牌认证只比较签名、过期时间和 Redis 中的旧令牌，没有撤销用户会话或比较凭据版本。`password_updated_at` 仅用于密码到期提示。
- 复现：用真实认证/改密服务和内存 DAO、缓存，先签发并认证令牌，再正确修改密码，随后用原令牌调用 `get_current_user`，仍然成功返回原账号。缓存删除次数为 0。未修改任何真实账号。
- 影响：用户改密后，另一设备或被盗的旧会话仍可在原有效期内使用；密码恢复不能立即收回访问。
- 修复：改密/管理员重置后撤销该用户的旧会话，或引入可比较的凭据版本；明确是否只保留重新签发的当前会话。兼容允许多设备登录时的会话索引。
- 验收：两设备登录后改密，旧设备下一次请求必须失效；不能误踢其他用户；管理员重置同样覆盖。

### 4. [P1] 部署入口限制 1MB，与资料上传支持 16MB 冲突

- 位置：`deploy/nginx/postgres.conf:1`；`frontend/src/views/portal/pages/KnowledgeView.vue:148`。
- 原因：Nginx 配置未设置 `client_max_body_size`，继承默认 `1m`；应用资料上传允许 16MB。
- 复现：独立 Nginx 容器加载仓库原配置，在容器内部发送 `Content-Length: 2097152` 的合成上传请求，返回 `HTTP/1.1 413 Request Entity Too Large`。未调用实际 API，也未上传用户文件。测试容器已停止并移除。
- 影响：本地 Vite 上传可以成功，部署后超过 1MB 的常见 Word/PDF 资料在到达后端前即失败。
- 修复：对两个 API 前缀统一配置与应用上限匹配的请求体限制，并预留 multipart 开销；保持应用自身严格限制。
- 验收：经部署 Nginx 实测 2MB、边界大小和超过业务上限的文件；正确显示失败原因。
- 默认值依据：[Nginx client_max_body_size 官方文档](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)。

### 5. [P1] Compose 默认扫描配置在自己的环境中不可用

- 位置：`docker-compose.pg.yml:53`、`:70`、`:98`、`:109`；`backend/src/app/system/services/file_scan.py:50`。
- 原因：API 和 Worker 环境为 `dockerpg`，扫描模式默认 `basic`；但代码只允许 dev/test/local 等环境使用 basic。默认外部扫描命令为空，镜像也没有提供完整外部扫描部署。
- 复现：使用合成文本文件，设置与 Compose 相同的 `app_env=dockerpg`、扫描模式 basic、空命令，实际扫描服务返回 `pending` 和“正式环境不能使用基础文件检查”。
- 影响：按默认 Compose 部署后，上传资料无法进入后续解析、下载和 AI 使用流程。这是配置冲突；现有扫描限制是安全保护，不能通过放宽生产检查来解决。
- 修复：提供可部署的外部扫描器、病毒库更新、明确命令和共享文件路径；启动预检对无效配置直接给出可操作错误。
- 验收：生产配置下正常文件通过；风险样本隔离；扫描器离线/超时仍阻止使用并明确提示；API 和 Worker 使用同一策略。

### 6. [P2] 导出中切换报告会轮询错误对象并误报超时

- 位置：`frontend/src/views/portal/pages/ReportEditorView.vue:552`。
- 原因：导出任务为报告 A 创建，但后续每次轮询都读取可变化的 `report.value.id`。同一编辑器组件切换到 B 后，轮询目标变为 B。
- 复现：提取仓库中的实际 `waitAndDownloadExport` 函数，以服务替身创建 A 的导出后切换到 B。A 已完成导出，但函数连续 60 次查询 B，不下载文件，最终抛出“导出任务处理超时”。
- 影响：任务可能已成功，页面却显示失败；用户可能重复创建导出。创建/轮询/下载所对应的报告不再一致。
- 修复：开始时冻结报告 ID、标题和草稿状态；切换路由后将结果放回对应报告记录，避免旧任务刷新新报告的界面。
- 验收：导出 A 后切到 B、返回 A、离开编辑器分别测试；不得把 A 的状态写到 B，也不能错误宣称 A 失败。

### 7. [P2] 同步模型调用的超时超过部署代理预算

- 位置：`deploy/nginx/postgres.conf:29`、`:39`；`frontend/src/api/pipeline/intelligence.js:206`；`backend/src/app/research/services/model_generation.py:100`；`backend/src/app/research/services/digest_screening.py:121`。
- 原因：简报复筛在 HTTP 请求内等待模型返回；前端允许 135 秒、模型允许至 120 秒，但代理未设置 `proxy_read_timeout`，继承默认 60 秒。如果上游 60 秒内没有任何响应字节，代理先关闭连接。
- 影响：合法配置的较慢复筛、翻译或改写可能被前端视为失败；后端调用仍可能已经执行。后台队列生成正文的轮询请求不等于这条同步调用链，不能用生成队列测试替代本项验收。
- 证据等级：源码调用链与官方默认值核对；本轮没有触发真实付费慢模型调用，也没有把线上 504 当作已观察事实。
- 修复：优先把长耗时操作改为可恢复任务；若保留同步方式，统一代理、前端和模型预算，并处理断开连接后的结果与幂等性。
- 验收：部署入口接合成慢上游，覆盖超过 60 秒的返回、断线与重试；不得重复消费同一筛选批次。
- 默认值依据：[Nginx proxy_read_timeout 官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)。

### 8. [P2] Linux 镜像缺少中文字体，PDF 退回未嵌入字体

- 位置：`backend/src/app/research/services/exporters.py:103`、`:120`；`backend/src/app/research/services/digest_export.py:229`；`deploy/docker/backend.pg.Dockerfile:1`。
- 原因：导出优先使用宿主机字体，找不到时退回 `STSong-Light` CID 字体；镜像没有安装中文/仿宋字体。当前本地后端镜像中的候选 Linux 字体路径也均不存在。
- 复现：模拟所有候选字体文件不存在，调用实际字体选择逻辑创建合成 PDF；提取字体结果为 `STSong-Light`、嵌入字节数 0。
- 影响：本机 macOS 的导出验收不能保证 Linux 部署后同样的字形与排版。没有相应 CJK 支持的阅读器可能显示不一致；不能断言所有阅读器都会乱码。
- 修复：选用有相应分发授权、覆盖目标字形的字体，随镜像安装或以受控卷提供并实际嵌入；缺失字体时明确预检失败，避免静默改变交付格式。
- 验收：在实际 Linux 镜像生成多页周报/月报和科研报告，核对字体嵌入、正文行距、标题、行业洞察及来源跨页，并与已确认示例进行视觉比对。

## 不合理或尚未完成的部分

以下不计入上面的 8 项已确认问题，建议作为后续完善项：

1. **生成系统缺少独立运行告警。** `/health/ready` 只证明 PostgreSQL、Redis 可用，Worker 没有心跳/积压指标的健康检查；API、Redis、前端 Compose 服务也没有与 Worker 同样的重启策略。需要独立观测 Worker 存活、队列等待时间和失败率，不能把 ready 绿色解释为生成服务正常。应隔离演练 Worker 崩溃，不停真实业务进程。
2. **简报列表显示生成时间，却仍按更新时间排序。** `list_queries.py:124` 默认按 `Report.updated_at.desc()`；编辑旧简报后会影响位置。建议明确默认排序并支持表头排序，不能只从当前样本恰好有序就认定没有歧义。
3. **资料自动分类、语义检索仍是显式未接入能力。** `KnowledgeView.vue:119` 与 `SearchView.vue:15` 已明确提示，属于尚未完成的功能，不是接口已经工作。它们与简报按提示词自动过滤、分类是不同链路；不能混为一谈。图片模型当前未配置，属于可选运行配置。

部署前仍需按目标环境替换硬编码数据库地址，迁移数据库、上传目录和原有密钥，配置扫描器与模型服务，并单独做备份恢复及目标负载测试。本轮没有验证公网/TLS、真实服务器容量或外部服务 SLA。
