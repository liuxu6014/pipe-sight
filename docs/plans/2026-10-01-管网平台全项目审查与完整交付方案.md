## 1. 结论先行

### 1.0 当前工作树对历史结论的校正（2026-10-04）

本文件保留 2026 年 10 月 1 日的审查基线和当时的缺口判断，不能直接当作当前实现状态。当前工作树已经完成了以下增量，后续验收应以代码、数据库和运行态为准：

| 领域 | 当前实现判断 | 当前边界 |
| --- | --- | --- |
| 数据治理 | 已有 PostgreSQL 读写服务、质量问题登记、重复组处理、批量动作、审核队列和权限控制 | 仍需用真实账号完成浏览器端审核、驳回、重处理和发布验收；不能只凭页面存在判定正式交付 |
| Prompt 管理 | 已有版本保存、离线结构测试、发布和采集快照 | 离线结构测试不等于模型效果评测；固定数据集评测和回滚验收仍是后续工作 |
| 模型与路由 | 已接入 PostgreSQL 模型配置、加密密钥保存、服务商校验、场景主备路由、限额和调用审计 | 真实模型调用样本、备用模型故障切换和限额耗尽仍需在已授权 endpoint 上做运行态验收 |
| 数据过滤 | 采集阶段先执行固定规则预过滤；外部交接由 InsightHub Worker 使用发布的 Prompt、路由和后端模型代理完成最终判断 | Crossref 本地采集路径仍是规则处理，不应在验收中宣称已经执行外部模型过滤 |
| 模型调用追踪 | 审计记录包含场景、路由、模型、Prompt 版本、采集运行 ID、负责人、耗时、状态和安全错误摘要 | 不保存 Prompt 正文、模型响应正文或 API Key；当前数据库没有真实模型调用记录时，应明确标记为“未形成运行样本” |
| 数据库与运行时 | 当前本地验收基线为 PostgreSQL/pgvector、Redis、PipeSight 后端、任务 Worker 和 InsightHub Worker | 旧版 MySQL/独立 InsightHub 目录说明仅作为迁移历史，不能覆盖当前 Compose 和代码事实 |

因此，下面的历史矩阵中标为“未实现”的条目，应先结合本节重新核对；本节也不把“代码已接入”直接升级为“正式交付完成”。

当前项目已经具备门户、登录、资讯与论文展示、资料管理、资料篮、科研任务、报告编辑、版本、图形、数据源、模板和 Prompt 等主要页面与基础数据对象，安全访问和数据处理也已有一部分真实实现。因此它不是静态原型，也不是需要推倒重做的空壳。

但按“普通用户能够利用真实、已审核的数据，稳定生成可追溯且可正式导出的科研成果；管理员能够完成数据治理、模型配置、任务恢复和运行监管”的标准，当前只能定位为**可演示的内部试用基线**，不能定位为“功能完整”或“正式交付完成”。

在 2026 年 10 月 1 日基线下，四个最主要的交付断点是：

1. 采集内容全部停留在待审核状态，而数据治理页是静态数据，没有真实审核、驳回、合并、重索引和发布闭环。
2. 模型配置页、场景路由和模型调用指标是静态数据；科研正文仍由固定模板与证据摘要拼接生成，没有真实模型网关和生成审计。
3. 科研生成任务已经具备数据库持久队列、租约、心跳、重试、取消、死信和重启恢复；科研生成、报告导出、资料解析、采集调度和 InsightHub 回执轮询已统一由独立 Task Worker 执行，API 仅保留接口和状态查询职责。
4. Word/PDF、导出快照、状态记录和哈希审计已经具备，但正式模板、定稿门槛、耐久任务执行和渲染回归仍未形成完整交付闭环。

如果只修界面而不补齐这四段，历史基线下的系统会出现“页面看起来完整，但没有可用数据、生成结果不是真实模型产物、重启可能丢任务、成果无法正式交付”的问题；当前是否仍然存在，应按本节校正后的代码和运行态逐项复验。

## 4. 总体业务闭环审查

目标主链路应为：

```text
数据源/爬虫
  → 原始内容入库
  → 标准化、过滤、去重、分类、质量检查
  → 人工审核与发布
  → 用户检索/详情/收藏/资料篮
  → 创建科研任务或周期简报
  → 持久任务执行与模型生成
  → 引用和质量检查
  → 编辑、版本、图形
  → 定稿
  → Markdown/Word/PDF 导出与审计
```

当前真实状态为：

```text
数据源/采集（部分真实）
  → 数据处理（已有基础）
  → 审核发布（缺失，数据停在 pending）
  → 用户端真实数据（因此被阻断）
  → 创建页和任务对象（已有）
  → 持久任务执行 → 按配置进行模型生成或证据模板编排
  → 编辑/版本/图形（已有基础）
  → Markdown/Word/PDF（已有，含持久导出记录）
  → 正式模板、定稿和可恢复交付（仍需完善）
```

因此第一开发优先级不是继续增加首页组件，而是打通“审核发布—真实生成—可靠执行—正式导出”。

## 5. 分模块审查与完善方案

### 5.1 登录、账号、角色和权限

**已观察到的基础**

- 登录、验证码、用户、角色和菜单沿用现有 RuoYi 权限体系。
- 管理端数据源、模板、Prompt 和任务接口使用管理端身份依赖。
- 用户资料、工作区、科研任务和报告按当前用户进行对象查询。
- 私有上传目录未整体暴露为匿名静态目录，下载走受控接口。

**缺口与风险**

- 尚未用管理员、普通用户甲、普通用户乙完成当前版本的跨账号浏览器验收。
- 管理页面由前端常量路由暴露，仍需逐接口验证普通用户不能绕过页面直接写入。
- 未形成角色权限矩阵、最小权限初始化脚本和生产账号交付流程。
- 模型密钥、数据库密码、传输加密和日志脱敏没有形成统一生产策略。

**完善方案**

1. 建立 `pipeline:data:*`、`pipeline:source:*`、`pipeline:template:*`、`pipeline:model:*`、`pipeline:task:*` 等细粒度权限，不只区分登录与未登录。
2. 所有写接口以后端权限为准；前端菜单隐藏只作为体验优化。
3. 对资料、任务、报告、版本、图形、导出文件逐对象执行 owner/public/authorized 校验。
4. 增加三账号权限回归测试，覆盖列表、详情、下载、引用、更新、版本恢复和导出。
5. 登出和换号时清除门户 Pinia 数据、未完成请求、资料篮和本地草稿作用域，防止延迟响应污染新账号。
6. 生产环境使用外部密钥注入，禁止默认 root 密码和明文模型密钥进入仓库或接口响应。

### 5.2 门户首页、导航和信息架构

**已观察到的基础**

- 首页、资讯、论文、科研工作台、情报简报、知识库和个人工作区路由完整。
- 当前导航已去掉知识问答入口，符合本阶段范围。
- 页面具备响应式样式、空状态、加载状态和部分 ARIA 标签。

**缺口与风险**

- 首页价值仍依赖已发布真实数据；当前全部内容待审核时，用户看到的不是完整业务能力。
- 部分页面仍保留 9–12px 的说明文字，管理端密集信息在普通显示器上可读性偏低。
- 编辑器基于 `contenteditable`，需要更完整的键盘、焦点、标签和保存状态支持。
- 部分空状态只告知“没有内容”，没有给出下一步动作或权限/审核原因。

**完善方案**

1. 首页只展示真实接口数据；无已发布数据时明确提示“内容待管理员审核发布”，不回退为容易被误认为真实的演示数据。
2. 将全局导航控制在“发现资料—组织资料—创建成果—管理成果”四层语义，减少科研任务、报告和简报入口的重复认知。
3. 管理端正文最小字号建议 13px，说明文字不低于 12px；关键状态不能只用颜色区分。
4. 所有异步按钮统一提供提交中、成功、失败、重试和重复点击防护。
5. 补齐键盘可操作、可见焦点、表单错误定位、读屏标签和移动端 44px 点击区域。
6. 建立 1366×768、1920×1080、平板和手机四档视觉回归基线。

### 5.3 资讯、论文、详情与全局搜索

**已观察到的基础**

- 后端有统一情报列表和详情接口。
- 普通用户只读取已审核内容的设计方向正确。
- 资讯、论文列表与详情页已接入真实接口。

**缺口与风险**

- 情报目录已改为数据库过滤、计数和按页候选读取，再在有限候选内合并排序；后续若新增跨表复杂排序，继续沿用数据库分页策略，禁止恢复为全量内存切页。
- 全局搜索已改为服务端统一检索、按权限返回并分页，首页只读取有限首屏候选，不再把全部资讯加载到浏览器。
- 日期范围和技术方向筛选已下沉到数据库查询，返回总数与分页结果保持一致；统一搜索的相对时间按各类型的真实时间字段精确过滤：资讯使用来源 `published_time`、论文使用平台 `published_at`、内部资料和报告使用 `update_time`；论文目录仍使用 `publication_year` 表示论文原始发表年份。
- 统一检索已建立 PostgreSQL `pg_trgm` 检索索引并保留 `ILIKE` 语义：英文/ASCII 直接使用原文索引，中文使用 `pipeline_utf8_hex` UTF-8 编码辅助索引预筛，再由原文 `ILIKE` 做最终校验。稳定游标和命中上下文摘要片段已完成；中文分词全文检索、词法分析仍未完成。游标按用户、筛选条件、相关性、时间、类型、ID绑定并消费 `nextCursor`，摘要优先展示命中的摘要或正文片段并保留安全结构化高亮，避免跨查询误用游标、低相关候选挤占首屏或长正文撑大结果卡片。
- 来源字段、发布时间精度、原文 URL、DOI、摘要和全文级别还没有统一的真实性约束。

**完善方案**

1. 新增服务端统一搜索接口：`GET /pipeline/search`，当前支持 `keyword/type/source/dateRange/directions/pageNum/pageSize/cursor`，连续翻页使用响应中的 `nextCursor`；`pageNum` 保留用于兼容和随机跳页，并限制为 100 页以避免深分页导致候选集无限增长。
2. PostgreSQL 使用原文 `pg_trgm` GIN 索引覆盖英文/ASCII，并使用 UTF-8 编码辅助 `pg_trgm` 索引覆盖中文子串；中文分词、词法分析需求达到阈值后再建设二元/三元词索引或评估专用搜索表、OpenSearch，不提前引入复杂基础设施。
3. DAO 层完成数据库分页、计数和排序，禁止把全量数据拉入 Python/浏览器切页。
4. 建立字段级内容层级：`metadata/abstract/fulltext`，不能把摘要标为全文。
5. DOI、URL、发布日期和来源名称保留原始值、规范值和抓取时间；缺失显示“未知”，不猜测补全。
6. 搜索结果只返回当前用户有权访问且已发布的内容，详情必须独立鉴权和加载。

### 5.4 数据源、采集运行和爬虫对接

**已观察到的基础**

- 数据源 CRUD、手动执行、cron 调度、运行记录和 InsightHub 交接已有真实实现。
- 调度避免同源重复进入，失败运行能够入库。
- 数据源可绑定已发布的数据过滤 Prompt 快照。

**缺口与风险**

- 2 个数据源已有 2 次失败，但缺少完整告警、失败分类、重试策略和运营处置界面。
- 爬虫输入输出缺少正式版本化契约，字段或枚举变化容易造成静默丢数。
- 当前固定容器名会造成多工作区 Compose 冲突。
- 未建立来源授权、抓取频率、版权范围和停用流程。

**完善方案**

1. 固化采集适配器契约：运行 ID、来源 ID、外部唯一键、原始 URL、标题、正文层级、发布时间精度、作者、附件、原始负载摘要和错误码。
2. 以 `source_id + external_id` 为首选幂等键，规范 URL/DOI 和内容哈希作为辅助去重，不只依赖标题。
3. 为失败增加 `error_code/error_stage/retryable/next_retry_at/attempt_count`，实现指数退避和最大次数。
4. 后台任务页提供运行详情、失败样本、重新执行、停用来源和告警确认。
5. 增加来源授权字段和审计：允许抓取的内容层级、频率、保留期限、可否用于模型生成。
6. Compose 移除固定 `container_name` 或使用明确项目名，支持并行环境。

### 5.5 数据处理、过滤、去重、分类和质量评分

**已观察到的基础**

- 当前未提交改动已增加 HTML/文本/URL/DOI 规范化、内容哈希、SimHash、分类、质量评分、Prompt 快照和处理元数据。
- Prompt 有版本、离线结构测试和发布流程，采集运行可以保存 Prompt 快照。

**缺口与风险**

- 质量规则尚未通过真实数据集校准，分数阈值可能只是工程默认值。
- SimHash 能发现近似文本，但事件级重复、转载关系和主记录选择仍缺少治理闭环。
- Prompt 离线测试只验证结构，不代表外部模型过滤效果或安全性。
- 处理结果主要进入元数据，缺少可查询的质量问题队列和规则版本审计。

**完善方案**

1. 定义处理流水线版本：`normalize → validate → filter → deduplicate → classify → score → review`，每一步记录版本、输入摘要、输出和耗时。
2. 建立 200–500 条人工标注校准集，包含保留/丢弃、技术分类、重复组和字段质量；每次规则或 Prompt 发布必须回归。
3. 将规则结果和模型结果分开保存：规则失败不能被模型高分直接覆盖。
4. 增加质量问题数据结构，至少包含对象、问题码、级别、证据、建议动作、状态、处理人和处理时间。
5. 重复治理建立 `duplicate_group_id/master_id/relation_type/similarity`，合并不物理删除来源证据。
6. 处理规则和 Prompt 使用发布版本快照，支持按运行追溯和重放。

### 5.6 数据治理、审核和发布

**当前事实**

- 数据库 24 条情报全部为 `pending`。
- OpenAPI 没有资讯/论文审核、驳回、合并和重新索引接口。
- `frontend/src/views/pipeline/governance/index.vue` 的指标、问题列表和操作均为前端常量；“刷新”“批量治理”“确认处理”只修改本地状态并显示成功提示。
- 当前实现已将重复组列表按状态、组 ID 和成员实际引用的文章/论文 ID 分层查询，避免为了展示治理结果扫描无关的治理和内容记录；治理扫描仍需遍历内容计算重复指纹和质量指标，不能简单改成只取当前页。

这是当前最高优先级缺口，因为它直接阻断用户端真实数据。

**完善方案**

1. 新增治理接口：
   - `GET /pipeline/governance/issues`
   - `GET /pipeline/governance/records/{type}/{id}`
   - `POST /pipeline/governance/records/{type}/{id}/approve`
   - `POST /pipeline/governance/records/{type}/{id}/reject`
   - `POST /pipeline/governance/duplicate-groups/{id}/merge`
   - `POST /pipeline/governance/records/{type}/{id}/reprocess`
   - `POST /pipeline/governance/batches`
2. 为资讯和论文补充 `reviewed_by/reviewed_at/review_reason/published_at`，状态机限定为 `pending → approved/rejected`；已发布内容修改后回到待审或建立新版本。
3. 建立不可变审核记录，保存前值、后值、动作、理由、操作者和时间。
4. 批量操作必须预览影响范围、逐条返回结果，禁止全部成功的虚假提示。
5. 合并记录时保留所有来源、发布时间、原始 URL、抓取批次和哈希，用户端展示主记录及来源数。
6. 完成后对现有 24 条数据进行真实审核，不允许用 SQL 批量改成 approved 代替业务验收。

### 5.7 个人资料上传、解析、权限和下载

**已观察到的基础**

- 有上传、列表、详情、删除、重试和受控下载接口。
- 支持 TXT、MD、DOCX 和可搜索 PDF 的基础解析。
- 私有文件不再通过整个上传目录匿名暴露。

**缺口与风险**

- 通用上传服务限制为 50MB；知识资料上传按本地解析上限限制为 16MB，门户知识库和科研创建页已同步显示 16MB。
- 当前运行库没有资料样本，合法文件、扫描 PDF、加密 PDF、空文件、超限文件和失败重试没有完成实际验收。
- 上传已增加扩展名、文件头校验、流式大小限制、SHA-256 完整性摘要、临时文件隔离和失败清理；知识资料已增加 `pending/clean/quarantined/failed` 扫描状态，未通过扫描不会解析、下载或进入 AI 证据链。
- 已提供无 shell 的外部扫描命令适配器和超时结果处理；当前本机未配置 ClamAV/扫描命令，因此新资料会保持 `pending`，生产环境必须配置 `FILE_SCAN_COMMAND` 后才会进入 `clean`。
- 当前未接入 OCR、解析超时和独立进程隔离；资料创建与重新解析已移出 API 事件循环，本地解析已增加 DOCX ZIP 条目数/展开大小和 PDF 页数上限。
- 删除、撤权和报告引用之间的行为尚未完全定义。

**完善方案**

1. 资料上传前后端统一为 16MB、允许类型和数量限制；通用系统上传保留独立的 50MB 上限，避免影响头像等其他场景。
2. 上传分为 `uploaded/scanning/parsing/ready/failed/quarantined`，原文件进入非公开对象存储或受控目录。
3. 校验扩展名、MIME、魔数、压缩展开大小、页数、解析时间和文本字符数。
4. 接入批准的恶意文件扫描；未扫描通过的文件不能解析、下载或发往模型。
5. 明确内容层级：扫描 PDF 未启用 OCR 时显示“不支持全文解析”，不能标记 ready。
6. 增加 `allow_download/allow_generation/permission_scope/content_level` 的统一后端校验。
7. 报告引用使用不可变证据快照；源文件撤权后限制新任务使用，但历史报告保留合规快照和撤权标记。

### 5.9 模板、Prompt、模型和场景路由

**已观察到的基础**

- Prompt CRUD、测试、发布和采集快照已有真实接口。

**当前事实与缺口**

- `ai_models` 当前为 0 条，模型页却展示 4 个可用模型、调用量和响应时间。

### 5.10 科研任务创建、生成和证据链

**已观察到的基础**

- 创建向导包含模板、资料、生成选项和大纲。
- 后端有任务、进度、取消、重试、报告、引用和质量问题数据结构。
- 所选资料会按权限和可用状态解析为证据。

**缺口与风险**

- 当前正文由固定语句和轮换的证据摘要拼接，不是真实模型生成。
- 后端已禁止空资料范围创建科研生成任务；资料权限、解析状态、安全扫描和 AI 使用权限仍会在执行阶段再次校验，失效资料不会被静默替换为其他资料。
- 生成结果提交前和取消操作均使用任务行锁，避免取消竞态把已完成任务改回 `cancelled` 或让已取消任务继续发布报告。
- 篇幅、双语、图形等选项没有全部真实参与生成，容易形成空开关。
- 引用只是章节轮换，并未验证正文主张与证据片段语义一致。
- 创建接口没有业务幂等键，网络超时重试或双击可能创建多个逻辑任务。

**完善方案**

1. 增加任务草稿状态。无可用证据时可保存配置和大纲，但不能进入“有证据正文生成”。
2. 创建请求包含客户端幂等键，后端按 `user_id + idempotency_key` 唯一约束返回同一任务。
3. 固化任务输入快照：模板版本、Prompt 版本、模型路由版本、资料版本、权限结果、大纲和所有生成参数。
4. 生成分为大纲检查、章节检索、章节生成、引用对齐、质量检查、图形建议和成果组装，各阶段可重试且记录产物。
5. 证据按章节主题检索，不再简单轮换；每个关键事实关联精确片段、位置、源版本和内容哈希。
6. 双语、公开检索补充或图形能力未接通前保持禁用，并在页面说明原因。
7. 报告质量规则至少包括：无来源、来源过少、来源单一、引用失效、事实与证据不一致、必填字段缺失、预算不平和疑似幻觉。
8. 用户编辑正文后将相关引用检查状态标为过期，必须重新校验后才能正式定稿。

### 5.15 任务队列、调度和可靠性

**当前事实**

- 科研任务先写入 `generation_tasks`，由单领导者 APScheduler 扫描并按数据库租约领取；接口请求不再直接依赖 `BackgroundTasks`。
- 任务已记录尝试次数、租约持有者、租约到期时间和下次重试时间；心跳会续租，租约过期后可重新领取，通用异常最多自动重试 3 次。
- 取消已记录 `cancel_requested_at`：运行中的任务先提交协作式取消请求，执行器在阶段边界停止，调度器也不会重新执行已请求取消的任务。
- 自动重试耗尽的瞬态异常进入 `dead_letter` 人工处理状态，与不可自动重试的业务失败区分；人工重新生成会重新建立新的自动重试窗口。
- 后端重启后，独立 Worker 可恢复 queued 和租约过期的科研任务、导出任务和资料解析任务；数据源 Cron 会在 Worker 启动时重新注册，InsightHub 回执轮询也随 Worker 恢复。采集来源和交接运行也持有 PostgreSQL 租约，支持多 Worker 部署时跨进程防重。

**完善方案**

1. 科研生成、导出和资料解析已放入基于 PostgreSQL 租约的独立持久执行器；采集与回执轮询也已从 API 调度器移入独立 Worker，并为来源和交接运行补充数据库租约，避免 API 重启影响后台业务任务，也避免多个 Worker 重复执行。
2. 当前调度器领取任务时设置租约和心跳；租约过期后安全重新领取。后续补充跨节点 Worker 的领导者切换和容量控制。
3. 每个阶段产物幂等写入；重复投递不能创建重复报告或重复导出。
4. 取消操作记录 `cancel_requested_at`，worker 在阶段边界检查；完成与取消竞态由数据库状态机裁决。
5. 启动时恢复 queued 和租约过期任务；超过重试次数进入 `dead_letter` 人工处理状态，保留错误信息和尝试次数，允许人工修正后重新生成。
6. 任务日志区分用户可见进度和运维诊断，敏感正文与密钥不入日志。
7. 已验证科研任务在真实 PostgreSQL 中由调度器领取并完成；仍需加入断网、模型超时、Redis 中断、数据库短暂故障和重复投递测试。

### 5.16 安全、隐私和合规

**当前主要问题**

- Compose 使用 `root/root`，并设置 `TRANSPORT_CRYPTO_ENABLED=false`。
- 前后端缺少生产安全配置基线。
- 上传文件、外部模型、来源版权、操作审计和日志保留尚未形成完整制度与技术约束。

**完善方案**

1. 开发、测试、生产配置分离；生产强制随机数据库凭据、TLS、传输加密、Secure/HttpOnly/SameSite Cookie 和受信代理配置。
2. 配置 CORS、CSRF、上传大小、请求体大小、速率限制和登录失败策略。
3. 私有资料发送模型前执行端点白名单和数据分类策略；未经批准的端点不得接收正文。
4. 对登录、下载、模型配置、审核、导出、删除和权限变更保留操作审计。
5. 日志脱敏访问令牌、Cookie、数据库密码、API Key、私有正文和文件路径。
6. 依赖、镜像和密钥扫描进入 CI；高危问题阻断发布。
7. 定义原文件、解析文本、引用快照、模型日志、导出文件和审计日志的保留与删除策略。

### 5.17 部署、监控、备份和恢复

**已观察到的基础**

- Docker Compose 可以启动前端、后端、MySQL 和 Redis。
- MySQL 和 Redis 有健康检查。

**缺口与风险**

- 前端和后端没有 Compose 健康检查，`depends_on` 也不能代表应用可用。
- 没有当前项目的 CI 工作流、自动发布、回滚包和环境检查。
- 没有可执行并已演练的 MySQL、文件、Redis/队列和导出对象备份恢复流程。
- 没有统一指标、结构化日志、告警、SLO 和容量基线。

**完善方案**

1. 增加 `/health/live` 和 `/health/ready`；ready 检查数据库、Redis、迁移版本和必要存储。
2. 前端 Nginx 增加健康端点；Compose 按健康状态依赖。
3. CI 至少执行后端格式/静态检查/测试、前端安装/构建/测试、迁移检查、镜像构建和依赖扫描。
4. 监控请求量、错误率、P95、队列长度、任务失败率、采集失败率、模型耗时、数据库连接和磁盘占用。
5. 备份 MySQL、原始文件、解析文本和导出文件；明确 RPO/RTO，并按季度做恢复演练。
6. 发布采用版本镜像和迁移前备份；回滚必须兼容新字段，不能靠删除用户成果恢复。

### 5.18 测试、验收和文档

**当前事实**

- 后端已有较多领域、控制器、调度、数据库和 CLI 测试文件。
- 前端存在源码结构测试和构建脚本，但本轮本地依赖缺失，未得到当前通过证据。
- README 仍描述知识问答和已不存在的接口，部分“后续规划”与当前实现不一致。
- `pipeline_service.py` 保留旧静态演示服务，主要被旧测试引用，容易造成实现判断混乱。

**完善方案**

1. 固定可重复的本地测试环境，锁定 Python/Node 版本和依赖安装命令。
2. 测试分层：单元测试、DAO/迁移测试、API 集成测试、浏览器 E2E、权限测试、故障注入、性能测试和导出视觉检查。
3. 浏览器 E2E 覆盖“审核发布 → 搜索详情 → 加篮 → 创建任务 → 任务完成 → 编辑 → 版本 → 导出”。
4. 三账号权限测试和 Web 进程重启恢复测试作为发布阻断项。
5. 删除或隔离旧静态 `PipelineService`，避免与真实领域服务同时存在。
6. 清理 README 中知识问答、旧端点、演示数据和过期完成状态；补充架构、启动、账号、数据初始化、测试、备份和恢复说明。
7. 所有交付结论附环境、commit、数据库迁移版本、测试命令、结果、截图和导出样例。
