# 管网项目设计管理系统数据库设计方案

日期：2026-07-27

> 命名说明：本文是早期完整规划，使用 `pipeline_` 作为业务表前缀。当前可落地实现已按“全系统、少表、名称清晰”重新收敛，实际表名和用户/权限/AI/日志全量清单以 [2026-08-14-full-system-database-design.md](2026-08-14-full-system-database-design.md) 为准。

## 1. 设计结论

本方案以当前项目的 PostgreSQL 版本为目标数据库，复用现有 RuoYi 基础表。本文的 `pipeline_` 表名仅代表早期规划，当前 SQL/ORM 已改用 `knowledge_files`、`news_articles`、`papers`、`generation_tasks` 等明确名称。

系统数据链路如下：

```text
你负责的爬虫和论文采集服务
        |
        v
采集信源/爬虫配置 -> 采集运行记录 -> 原始数据记录
                                      |
                                      v
                         数据处理方清洗、去重、分类、评分
                                      |
                                      v
                 新闻/公众号、论文、标签、实体、向量和处理结果
                                      |
                                      v
              你负责的全栈系统：检索、展示、知识库、报告和导出
```

本方案采用以下关键决策：

1. 系统基础用户、角色、菜单、部门、定时任务和操作日志直接复用现有 `sys_*` 表，不再建立第二套用户权限表。
2. 新闻和微信公众号文章统一进入资讯域，通过 `content_type` 或 `news_type` 区分 `NEWS` 和 `WECHAT`。
3. 论文先存储合法获取的元数据；受版权限制的全文不由系统自动抓取。开放获取链接或用户通过授权渠道上传的 PDF，才进入全文解析流程。
4. 爬虫表只登记和管理已经接入的一百多个爬虫。界面支持启停、调度、频率、重试和运行查看，但本期不提供新增爬虫代码或新增爬虫记录的操作。
5. 原始采集记录是两位开发者之间的交付边界。采集服务只负责写入原始记录和采集状态，数据处理服务负责生成标准化内容、分类、评分和标签结果。
6. 新闻处理规则必须数据化，过滤、分类、评分、等级和后续动作都通过数据库配置，不通过修改代码完成；启用版本只能新增版本记录，不能原地覆盖历史规则。
7. 报告、方案、论文生成结果按创建人隔离。普通用户只能查询、编辑和导出自己创建的报告。
8. PostgreSQL 是业务事实库。全文检索和向量检索可以接 Elasticsearch、Milvus 或 pgvector，但外部索引只保存索引，不能替代 PostgreSQL 的业务记录。

## 2. 现有表复用范围

以下表已经存在于 `backend/sql/ruoyi-fastapi-pg.sql`，不应重复创建：

| 领域 | 复用表 |
| --- | --- |
| 组织和用户 | `sys_dept`、`sys_user`、`sys_post` |
| 权限 | `sys_role`、`sys_menu`、`sys_user_role`、`sys_role_menu`、`sys_role_dept`、`sys_user_post` |
| 配置和字典 | `sys_config`、`sys_dict_type`、`sys_dict_data` |
| 日志和调度 | `sys_oper_log`、`sys_logininfor`、`sys_job`、`sys_job_log` |
| 通知 | `sys_notice` |
| AI 模型 | `ai_models`、`ai_chat_config` |

`gen_table` 和 `gen_table_column` 继续作为代码生成器元数据表使用，不属于平台业务数据。

现有 `sys_oper_log` 负责常规后台操作日志；对需要保存对象 ID、前后值和数据访问证据的业务审计，另增加 `pipeline_audit_event`，两者职责不同。

现有 `module_pipeline` 的列表、来源、任务、报告和知识库接口目前返回确定性样例数据，后续应改为 DAO 查询本文的业务表。论文接口已迁入 `app.research`，旧 `module_manuscript` 仅作兼容转发；论文任务写入 `generation_tasks`、报告写入 `reports`、版本写入 `report_versions`，不再使用 `_jobs` 内存字典。

## 4. 通用字段和命名约定

### 4.1 通用字段

除运行日志、关联表和分区健康表外，业务主表统一建议包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `bigint generated by default as identity` | 内部主键 |
| `created_at` | `timestamptz` | 创建时间 |
| `updated_at` | `timestamptz` | 最后修改时间 |
| `created_by` | `bigint` | 创建人，关联 `sys_user.user_id` |
| `updated_by` | `bigint` | 修改人，关联 `sys_user.user_id` |
| `is_deleted` | `boolean` | 业务数据逻辑删除标志，默认 `false` |

系统表继续使用 RuoYi 现有的 `create_time`、`update_time`、`create_by`、`update_by` 和 `del_flag` 字段，不做风格迁移。

### 4.2 类型约定

- 时间统一使用 `timestamptz`，写入 UTC，前端按用户时区显示。
- 状态统一使用 `varchar` + 字典值，不建议在第一版使用 PostgreSQL enum，避免后续状态变更需要改类型。
- 复杂的采集器配置、规则条件、模型参数和图形 JSON 使用 `jsonb`，查询频繁的字段必须单独提列。
- 外部链接使用 `text`，不要使用过短的 `varchar(255)`。
- 所有哈希保存算法名和结果，例如 `hash_algorithm`、`content_hash`，避免后续从 SimHash 切换到 SHA-256 时无法区分。
- 多对多关系必须使用关联表，不在主表中保存 ID 数组。旧设计中的 `target_source_ids`、`cluster_news_ids`、`source_material_ids` 应改为关联表。

## 5. 采集域表设计

### 5.1 `pipeline_source` 数据源清单

一行代表一个已确认的来源，例如 WOS 论文库、某个新闻网站、某个微信公众号。它不是爬虫代码表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `source_code` | varchar(64) | 来源编码，唯一 |
| `source_name` | varchar(256) | 来源名称 |
| `source_type` | varchar(32) | `PAPER_DB`、`NEWS_SITE`、`WECHAT_MP` |
| `home_url` | text | 来源首页或 API 地址 |
| `domain` | varchar(256) | 域名 |
| `account_name` | varchar(256) | 公众号名称，网站来源为空 |
| `authorization_status` | varchar(32) | `AUTHORIZED`、`PENDING`、`UNAVAILABLE` |
| `target_scope` | jsonb | 期刊、栏目、关键词、年份等目标范围 |
| `is_enabled` | boolean | 来源是否参与采集 |
| `change_reason` | text | 调整来源配置的原因 |
| `created_at`、`updated_at` | timestamptz | 时间字段 |

约束：`source_code` 唯一；网站域名和公众号名称可重复但必须结合来源类型校验。

### 5.2 `pipeline_crawler` 现有爬虫登记表

一行代表一个已经编写并部署的爬虫。该表是本项目中“管理一百多个爬虫”的核心表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `crawler_code` | varchar(128) | 爬虫编码，唯一，对应代码中的 adapter key |
| `crawler_name` | varchar(256) | 页面显示名称 |
| `source_id` | bigint | 关联 `pipeline_source.id` |
| `data_type` | varchar(32) | `NEWS`、`WECHAT`、`PAPER` |
| `adapter_class` | varchar(512) | 适配器类或模块路径 |
| `code_version` | varchar(128) | 当前部署代码版本 |
| `enabled` | boolean | 是否允许爬取，支持单个/批量修改 |
| `runtime_status` | varchar(32) | `READY`、`RUNNING`、`PAUSED`、`ERROR` |
| `cron_expression` | varchar(128) | 调度表达式 |
| `priority` | integer | 优先级，数值越大越优先 |
| `rate_limit_rps` | numeric(8,2) | 每秒请求上限 |
| `max_concurrency` | integer | 最大并发数 |
| `timeout_seconds` | integer | 单次请求超时时间 |
| `retry_max` | integer | 最大重试次数 |
| `circuit_breaker_config` | jsonb | 熔断阈值和恢复窗口 |
| `crawl_config` | jsonb | 分页、栏目、关键词、年份、字段提取等配置 |
| `auth_secret_ref` | varchar(256) | 密钥引用，不保存明文密钥 |
| `last_run_at`、`next_run_at` | timestamptz | 最近/下次执行时间 |
| `last_error` | text | 最近错误 |
| `created_at`、`updated_at` | timestamptz | 时间字段 |

权限边界：后台可以查询、启停和修改运行参数，但不提供新增、删除或上传爬虫代码的接口。初始一百多个爬虫通过种子数据导入；新增爬虫必须由你开发并通过部署或数据库迁移登记。

### 5.3 `pipeline_crawl_run` 爬虫执行记录

一行代表一次实际执行，区别于 `pipeline_crawler` 的长期配置。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `crawler_id` | bigint | 关联爬虫 |
| `trigger_type` | varchar(16) | `CRON`、`MANUAL`、`RETRY`、`BACKFILL` |
| `run_mode` | varchar(32) | `INCREMENTAL`、`FULL_BACKFILL`、`MANUAL_RANGE` |
| `status` | varchar(16) | `PENDING`、`RUNNING`、`SUCCESS`、`PARTIAL`、`FAILED`、`CANCELLED` |
| `worker_id` | varchar(128) | 执行节点 |
| `cursor_before`、`cursor_after` | jsonb | 增量游标或最后更新时间 |
| `started_at`、`finished_at` | timestamptz | 执行时间 |
| `fetched_count` | integer | 抓取总量 |
| `new_count` | integer | 新增原始记录数量 |
| `duplicate_count` | integer | URL/内容去重数量 |
| `failed_count` | integer | 失败数量 |
| `retry_count` | integer | 已重试次数 |
| `error_message` | text | 错误信息 |
| `run_detail` | jsonb | 页数、HTTP 状态、配额等明细 |

索引：`(crawler_id, started_at desc)`、`(status, started_at desc)`。

### 5.4 `pipeline_file_object` 文件对象元数据

文件本体放 MinIO 或本地对象存储，数据库只保存元数据。新闻 HTML 快照、公众号图片、用户上传 PDF、报告导出文件和路线图都复用此表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `object_key` | text | 对象存储 key，唯一 |
| `bucket_name` | varchar(128) | bucket |
| `original_name` | varchar(512) | 原始文件名 |
| `mime_type` | varchar(128) | MIME 类型 |
| `file_ext` | varchar(32) | 文件扩展名 |
| `file_size` | bigint | 字节数 |
| `sha256` | char(64) | 文件哈希 |
| `owner_user_id` | bigint | 所有人 |
| `visibility` | varchar(16) | `PRIVATE`、`DEPT`、`GLOBAL` |
| `purpose` | varchar(32) | `RAW_SNAPSHOT`、`PAPER_FULLTEXT`、`KNOWLEDGE`、`EXPORT`、`IMAGE` |
| `status` | varchar(16) | `UPLOADING`、`READY`、`FAILED`、`DELETED` |
| `created_at` | timestamptz | 创建时间 |

### 5.5 `pipeline_raw_record` 原始数据交付表

该表是你和数据处理方之间最重要的边界。采集服务只负责写入原始内容、来源和指纹，处理服务读取 `PENDING` 记录并回写处理状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `crawl_run_id` | bigint | 关联采集执行记录 |
| `source_id` | bigint | 关联来源 |
| `external_key` | varchar(512) | 来源内部 ID、DOI、URL 或文章永久 ID |
| `data_type` | varchar(32) | `NEWS`、`WECHAT`、`PAPER` |
| `source_url` | text | 原始链接 |
| `raw_title` | text | 原始标题 |
| `raw_content` | text | 原始正文或摘要 |
| `raw_payload` | jsonb | 完整 API JSON/XML 转换结果 |
| `snapshot_file_id` | bigint | HTML/XML 快照文件 |
| `content_hash` | varchar(128) | 内容指纹 |
| `hash_algorithm` | varchar(32) | `SIMHASH64`、`SHA256` 等 |
| `fetched_at` | timestamptz | 采集时间 |
| `process_status` | varchar(24) | `PENDING`、`CLAIMED`、`PROCESSING`、`COMPLETED`、`FAILED`、`REJECTED` |
| `process_attempts` | integer | 处理尝试次数 |
| `claimed_at` | timestamptz | 处理方领取时间 |
| `processed_at` | timestamptz | 完成时间 |
| `processor_version` | varchar(128) | 处理服务版本 |
| `last_error` | text | 处理错误 |

唯一性建议：`(source_id, external_key)` 唯一；如果来源没有稳定外部 ID，则使用 `(source_id, content_hash)` 作为业务去重键。

### 5.6 `pipeline_processing_batch` 和 `pipeline_processing_item`

`pipeline_processing_batch` 记录一次清洗/分类/评分批次；`pipeline_processing_item` 记录批次内每条原始数据的状态。

`pipeline_processing_batch` 核心字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `batch_no` | varchar(64) | 批次号，唯一 |
| `stage` | varchar(32) | `CLEAN`、`STRUCTURE`、`CLASSIFY`、`SCORE`、`FULL_PIPELINE` |
| `processor_version` | varchar(128) | 数据处理方服务版本 |
| `rule_snapshot` | jsonb | 本批使用的规则版本快照 |
| `status` | varchar(16) | `PENDING`、`RUNNING`、`SUCCESS`、`PARTIAL`、`FAILED` |
| `input_count`、`success_count`、`failed_count`、`rejected_count` | integer | 处理统计 |
| `started_at`、`finished_at` | timestamptz | 执行时间 |
| `delivery_status` | varchar(16) | `NOT_DELIVERED`、`DELIVERED`、`ACKED` |
| `error_message` | text | 批次错误 |

`pipeline_processing_item` 核心字段：`batch_id`、`raw_record_id`、`target_type`、`target_id`、`status`、`rejection_reason`、`result_hash`、`started_at`、`finished_at`、`error_message`。其中 `target_type/target_id` 指向 `pipeline_news` 或 `pipeline_paper`，属于受控的多态引用，服务层必须校验目标存在。

## 6. 新闻和论文数据表设计

### 6.1 `pipeline_news` 新闻/公众号统一内容表

新闻网站和公众号使用同一张表，`news_type` 区分来源类型。建议该表按 `publish_time` 按月分区，近 3 个月放热表空间，3 至 13 个月放冷表空间，超过 13 个月按现有归档策略 detach，数据不删除。

### 7.5 `pipeline_score_scheme`、`pipeline_score_dimension`、`pipeline_score_level`

评分使用三层结构：评分方案 -> 评分维度 -> 等级区间。

评分等级名称和阈值由管理员配置，不在代码中固定为某一组分值。

### 7.6 `pipeline_content_analysis` 和 `pipeline_rule_hit`

`pipeline_content_analysis` 保存每次分析结果，不能只覆盖新闻当前字段，否则无法解释规则修改后为什么得分变化。

API Key 只允许保存在现有 `ai_models.api_key` 的加密字段中；`pipeline_ai_run` 不保存明文密钥。

### 10.3 翻译

`pipeline_translation_task`：`id`、`owner_user_id`、`source_file_id`、`source_type`、`source_id`、`source_language`、`target_language`、`file_type`、`status`、`model_id`、`created_at`、`finished_at`、`error_message`。

`pipeline_translation_version`：`id`、`translation_task_id`、`version_no`、`translated_text`、`translated_file_id`、`created_by`、`created_at`。

PDF 翻译必须先经过解析任务，不能把 PDF 二进制内容直接当作纯文本翻译。

### 10.4 `pipeline_audit_event` 业务审计

字段：`id`、`request_id`、`user_id`、`username_snapshot`、`operation_type`、`object_type`、`object_id`、`before_data`、`after_data`、`result`、`failure_reason`、`client_ip`、`user_agent`、`occurred_at`。

该表只追加写入，禁止业务接口 UPDATE/DELETE。至少记录登录、上传、查看全文、启停爬虫、修改过滤/评分规则、生成、编辑、回退、导出、删除和权限变更。

## 12. 状态和数据流约定

### 12.1 采集状态

```text
爬虫 enabled=true
    -> sys_job/调度器触发
    -> pipeline_crawl_run.RUNNING
    -> pipeline_raw_record.PENDING
    -> pipeline_crawl_run.SUCCESS/PARTIAL/FAILED
```

停用爬虫只影响后续调度，不删除历史 `pipeline_crawl_run` 和 `pipeline_raw_record`。

### 12.2 数据处理状态

```text
raw_record.PENDING
    -> processing_item.CLAIMED
    -> PROCESSING
    -> pipeline_news/pipeline_paper 写入
    -> content_analysis 写入
    -> raw_record.COMPLETED
```

处理失败必须保留原始记录，支持重试；不能因为处理失败删除或覆盖采集原文。

### 12.3 报告状态

```text
generation_task.DRAFT
    -> QUEUED -> RUNNING -> COMPLETED
    -> report.DRAFT
    -> report_version 保存
    -> 用户编辑/回退
    -> 导出
```

## 13. 索引、分区和存储策略

### 13.1 新闻分区

当前部署基线以 `166_pg环境文档.md` 为准：PostgreSQL 18.4、数据库 `newsdb`、表空间 `ts_hot/ts_cold`、pg_partman 5.4.3、pg_cron 1.6.7 和 pgvector 0.8.5。较早热冷方案中的 PostgreSQL 16、`news` 表和 `ts_ssd/ts_hdd` 仅作为历史验证材料，不能直接执行。本项目应新建迁移脚本，统一使用 `pipeline_news` 和当前部署基线。

建议：

- 按月对 `pipeline_news.publish_time` 做 RANGE 分区。
- 近 3 个月放热表空间，3 至 13 个月放冷表空间，超过 13 个月 detach 归档但不删除。
- 所有资讯列表和日报查询必须带时间范围，避免未来扫描所有分区。
- 向量表不跟随新闻正文分区，使用独立的 `pipeline_embedding` 或外部 Milvus collection。
- 分区表的关联不要依赖只包含 `id` 的外键；对跨分区、多类型资源统一通过服务层校验 `content_type + content_id`。

### 13.2 主要索引

| 表 | 索引 |
| --- | --- |
| `pipeline_crawler` | `crawler_code` 唯一、`enabled + runtime_status` |
| `pipeline_crawl_run` | `crawler_id + started_at desc`、`status + started_at desc` |
| `pipeline_raw_record` | `source_id + external_key` 唯一、`process_status + fetched_at`、`content_hash` |
| `pipeline_news` | `publish_time`、`source_id + publish_time`、`news_type + publish_time`、`importance_level + publish_time`、`content_hash` |
| `pipeline_paper` | `source_id + paper_uid` 唯一、`doi` 唯一、`publication_year`、`publication_name` |
| `pipeline_content_analysis` | `content_type + content_id + is_current`、`score_level_id + created_at` |
| `pipeline_content_tag` | `tag_id + content_type + content_id`、`content_type + content_id` |
| `pipeline_knowledge_document` | `knowledge_base_id + index_status`、`owner_user_id` |
| `pipeline_document_chunk` | `knowledge_document_id + index_version + chunk_no` 唯一、`text_hash` |
| `pipeline_generation_task` | `owner_user_id + created_at desc`、`status + created_at desc` |
| `pipeline_report` | `owner_user_id + updated_at desc`、`report_type + updated_at desc` |
| `pipeline_audit_event` | `occurred_at desc`、`user_id + occurred_at desc`、`object_type + object_id` |

### 13.3 全文和向量索引

PostgreSQL 保存业务正文和切块元数据，全文检索可将 `pipeline_news`、`pipeline_paper`、`pipeline_document_chunk` 同步到 Elasticsearch。向量服务可以先使用 pgvector，后续再切换 Milvus；切换只改变 `pipeline_embedding.vector_store` 和外部索引，不改变业务表。

向量模型、维度、距离算法仍必须在第一次建向量索引前确认。当前资料存在 `halfvec(768)` 和 `vector(1536)` 两种方案，不能同时把两种维度写入同一固定维度索引；在确认前，`pipeline_embedding` 只建立模型、维度、存储位置和索引状态等元数据，不创建最终 ANN 索引。

## 14. 权限和数据隔离

1. 用户登录、角色、部门和菜单使用 RuoYi 表以及现有 RBAC 机制。
2. 爬虫配置查看/编辑/启停使用菜单权限和按钮权限；批量停用、批量删除原始数据、修改评分规则和全量导出需要更高权限及二次验证。
3. 用户端新闻、论文列表可以按系统数据范围控制；用户只能查看被授权部门/知识库范围内的资料。
4. 报告、方案和论文生成任务按 `owner_user_id` 隔离，查询、编辑、版本回退和导出都必须在后端追加所有者条件。
5. 知识库使用 `PRIVATE`、`DEPT`、`GLOBAL` 三种可见性；文档默认继承知识库权限。
6. 文件下载必须校验对象所有者或知识库/报告权限，不能只凭 `file_object_id` 直接下载。
7. `pipeline_audit_event` 和 `sys_oper_log` 记录高风险操作，不能因为业务对象被逻辑删除而删除审计记录。

## 15. 两位开发者的数据库责任边界

### 15.1 你负责的表和能力

- `pipeline_source` 的来源展示、已有来源参数维护和启停。
- `pipeline_crawler` 的一百多个爬虫登记、检索、单个/批量启停和运行参数配置。
- `pipeline_crawl_run`、`pipeline_raw_record` 的采集写入和采集日志页面。
- 论文采集、论文元数据写入、合法全文上传和 `pipeline_paper_section` 调用。
- 所有全栈 API、管理页面、用户门户、权限、报告生成入口、知识库入口和导出。

### 15.2 数据处理方负责的表和能力

- `pipeline_processing_batch`、`pipeline_processing_item` 的处理批次和逐条状态。
- `pipeline_news`、`pipeline_paper` 中的清洗后字段和标准化字段。
- `pipeline_content_analysis`、`pipeline_content_tag`、`pipeline_rule_hit` 的处理结果。
- `pipeline_entity`、`pipeline_entity_mention`、`pipeline_entity_relation` 的抽取结果。
- 清洗、去重、分类、评分、摘要和质量状态的处理服务。

### 15.3 双方接口约定

- 采集服务写入 `pipeline_raw_record` 后，状态为 `PENDING`。
- 处理服务领取记录时使用锁或领取状态，避免重复处理。
- 处理服务不得删除原始数据；失败只更新处理状态和错误信息。
- 处理结果必须携带 `processor_version`、`analysis_version` 和规则版本。
- 全栈系统读取标准化结果，不在前端临时重复实现清洗、评分和分类逻辑。
- 数据库表结构变更必须通过 Alembic migration，不允许两人直接修改线上表结构。

## 16. 建表和迁移顺序

1. 按当前部署基线核验 PostgreSQL 18.4、`newsdb`、`ts_hot/ts_cold`、pgvector、pg_partman 和 pg_cron；若环境发生变化，只允许通过迁移配置调整，不执行旧的 `ts_ssd/ts_hdd` 脚本。
2. 先导入现有 RuoYi PostgreSQL 基础表和 AI 表。
3. 建立 `pipeline_source`、`pipeline_crawler`、`pipeline_crawl_run`、`pipeline_file_object`、`pipeline_raw_record`。
4. 通过种子数据登记一百多个已有爬虫，不提供新增爬虫的后台接口。
5. 建立处理批次、新闻、论文、作者、章节、引用、标签和分析规则表。
6. 先用一批真实采集数据完成采集方与处理方联调，再建立知识库、报告和导出表。
7. 建立搜索日志、Prompt、AI 调用、翻译、审计和备份记录表。
8. 为每一组表建立独立 Alembic revision，迁移命名使用 `pipeline_*` 前缀，禁止直接执行旧的 `setup_news.sql`。
9. 继续把剩余样例服务改为 DAO 查询；论文生成的内存 `_jobs` 已迁移为数据库任务和报告版本，后续重点是补齐资料证据关联与数据库分页查询。
10. 用“一个爬虫运行、一条新闻、一篇论文、一个报告任务、一个知识库文档”完成端到端验收。

## 17. 不建议现在建立的表

- GIS 管线资产、巡检工单、设备台账、空间轨迹等表：当前项目定位不是 GIS 或生产运维系统。
- 单独的 `news` 业务表：已有旧脚本只是 PostgreSQL 热冷测试方案，字段不满足本项目处理状态、分类、评分和权限要求。
- 单独的 `audit_log` 替代 RuoYi 日志：先复用 `sys_oper_log`，仅增加 `pipeline_audit_event` 补充业务对象级不可篡改审计。
- 把标签、来源、报告资料、热点新闻全部存成 ID 数组的表设计：数组无法维护外键、排序、来源快照和删除后的追溯关系。
- 在没有确定模型维度前直接创建 `vector(1536)` 或 `halfvec(768)` 的最终生产索引。

## 18. 第一版验收清单

- 能从 `pipeline_crawler` 读取一百多个爬虫，并完成单个和批量启停。
- 停用爬虫后不会产生新的定时 `pipeline_crawl_run`。
- 一次采集能写入 `pipeline_raw_record`，处理方能领取并回写完成/失败状态。
- 新闻网站和公众号内容能在 `pipeline_news` 中统一展示并区分类型。
- 论文列表能查询标题、作者、机构、期刊、年份、摘要、关键词和 DOI。
- 规则修改不需要代码发版，历史新闻可以预览过滤、分类和评分结果。
- 每条资讯可以追溯到原始记录、处理批次、规则命中、标签和评分明细。
- 用户生成的报告只能被本人查询、编辑、回退和导出。
- 报告版本、引用来源、导出文件和操作日志均可追溯。
- 数据库迁移可以在开发环境重复执行，并能通过 Alembic 版本回退。
