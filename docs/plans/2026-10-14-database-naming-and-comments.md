# PipeSight PostgreSQL 命名与注释规范化实施计划

> 本文件记录首次规范化阶段。后续已按用户要求将11张应用业务表改为短名称，原 `pipeline_*` 保留决定已被替代；当前规范见 [简短表名规范](../architecture/table-naming.md)，实际结构以最新数据字典为准。

## 目标与边界

目标库为 `172.16.4.183:5432/pipesight`，当前运行使用 PostgreSQL 18。保留数据、账号、主键值、外键关系、已有业务字段类型和权限范围，不重新初始化业务数据。数据库设计技能作为参考，采用 PostgreSQL 语法，不套用 MySQL 示例。

## 命名决策

- `public.sys_*`、`ai_models`、`ai_chat_config` 复用若依框架，保留既有名称及字段，避免破坏认证、菜单、字典、参数和模型配置。
- `public` 中的资料、任务、成果、采集、内容表沿用明确的业务复数名；`pipeline_*` 是情报管道的业务域限定，不是新增系统配置框架。`pipeline_model_route_usage` 的 usage 为不可数名词，保留。
- `news` 内去掉历史系统前缀及重复 schema 名，使用清晰的业务复数名。保留旧名兼容视图，不复制数据。
- 框架字段的 `create_time`、`update_time`、`del_flag` 及处理输入的历史字段保持兼容，不仅为统一风格批量改列名或改变时间语义。以精确注释解释历史字段、真实状态值和未启用用途。

## 执行步骤

1. 审计全部 `public`、`news` 业务表、调度/迁移基础表及兼容视图的表和字段备注。
2. 并行补齐应用 ORM/应用 SQL 与处理域 SQL 的显式中文注释。新字段若缺少注释，测试必须失败，不自动生成模糊占位说明。
3. 更新处理数据访问代码和初始化 SQL 到规范物理名，新增受控 Alembic 迁移，保留旧名兼容视图并同步备注。
4. 保障框架自动创建的调度表在新环境也带注释；新建环境和既有库升级均运行同一套备注定义。
5. 在隔离本地测试库验证旧名迁移、新库初始化、兼容查询、处理写入和注释零缺失。
6. 备份远程库，暂停本项目 API/任务 Worker，执行迁移后重启，核对登录、读取和 Worker 健康状态。
7. 导出可核对的数据字典和完整性核验结果。

## 风险和兼容约束

- 物理表改名不改变数据或外键 OID 关联。旧名视图用于兼容读取及普通单表写入，不保证 `ON CONFLICT`、DDL、分区管理等物理表专属操作；所有本仓库运行代码改用规范表名。
- 若同一历史名和规范名下同时已有物理表，迁移必须停止，不猜测、不合并、不删除。
- 不删除若依框架配置表，不将有版本、发布或审计语义的业务记录塞入 `sys_config`。
- 未确认业务含义的历史字段明确标为历史兼容/当前未使用，不能虚构状态含义。
- 密码、模型密钥和真实业务正文不进入数据字典或迁移日志。

## 验收

全部范围内对象及每个字段有非空且有意义的中文注释；物理表名符合决策表；旧名兼容视图不产生重复数据；主键、字段、索引、外键和行数保持一致；代码、SQL、ORM、远程 catalog 和导出的字典一致。测试通过和实际数据库核验分别报告。

## 后续维护约定

新增字段必须同时提供真实含义的中文注释；状态列注明实际枚举，计数/金额/大小列注明单位，JSON列说明结构和用途，敏感列注明边界。不能以字段名翻译或“扩展字段”占位代替业务说明。

应用侧在ORM声明注释，并同步应用注释SQL；处理侧同步建表SQL与处理注释SQL。既有部署的修改通过新的Alembic迁移执行，不仅修改已执行的历史迁移。新环境执行基础SQL后运行 `alembic upgrade head`，启动脚本与Compose均已接入该步骤。新增/修改后运行注释覆盖测试、数据库检查和字典导出；不得把连接凭据或真实业务正文放入字典。
