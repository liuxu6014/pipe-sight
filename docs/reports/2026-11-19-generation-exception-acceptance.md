# 生成异常流程实际验收

日期：2026-11-19。基线 `f26ced46d28022072c2f940aec4d0fcaa003071e`。使用本地普通账号年糕，验证失败、重复重试、后台排队、切页、刷新及完成提醒；复现并修复两处问题。

后续再次复审补齐了 Worker 中断、租约过期和并发跟踪存储边界，见 [生成流程再次复审](2026-11-19-generation-rereview.md)。本文保留上一轮验收事实。

## 修复结果

1. **同一失败任务可以重复创建重试任务。** 修复前，任务 389 失败后，从旧页两次确认重新生成，分别创建了 391、392，都会调用模型。同页 loading 标志不能保护刷新、丢失响应或多标签页。现在后端锁定原任务行，以内部 `retry:<原任务编号>` 唯一请求键记录后继任务，重复请求直接返回同一个后继任务，不重新计费生成。后继任务也失败或被取消时，可从该后继任务继续明确重试，原记录仍保留；无需新增迁移。前端区分“新建排队”“复用已有任务”“重试已完成”的反馈。
2. **旧标签页可能覆盖其他标签页已经保存的完成提醒回执。** 本次曾观察到两个标签页重复提示同一结果。原因是仍在运行的标签页写入旧的 notified 集合，覆盖了另一个标签页的新回执。现在保存前合并同用户已存回执，避免旧队列状态抹掉已提醒记录；新增双实例交错更新的行为回归。修复后另建任务 402 实测，两受控标签页合计出现一次该任务提醒，另一页刷新后没有重复提醒。

## 故障制造与恢复边界

- 开始前只读检查应用库，排队和执行中任务均为 0，避免打断其他任务。
- 暂停正常本地 Worker，提交独立验收报告，使用既有公开资讯 20 与 2 章、600 字个人验收模板。
- 临时进程仅领取任务 389，在进程内使用无效凭据发起真实 DeepSeek 请求，供应商实际返回 HTTP 401。原模型地址、加密密钥、用途配置和 `.env` 均未修改；没有用成功样稿替代模型输出，也没有直接写任务状态制造失败。
- 故障进程结束后启动正常 Worker，恢复真实凭据解析。失败及取消任务不会自动重发可能计费的模型调用。
- 修复前复现产生的 391、392 通过网页“取消任务”停止，保留记录；均未被 Worker 领取，没有模型调用。没有删除历史任务或重置数据库。
